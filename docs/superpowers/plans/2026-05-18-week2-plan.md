# Week 2 Implementation Plan — Review Analysis + Eval Baseline

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enrich cafe rows with a stronger **review-based tagger** (`review_tagger_v2`), establish **JSON + DB prompt versioning** (`prompt_versions`), hand-author a **30-query golden set**, and run a **RAGAS-style baseline** that writes honest metrics to `docs/eval-results/`. Week 2 records numbers only; prompt iteration to hit targets is **Week 4** per spec.

**Builds on Week 1:** FastAPI + Postgres/pgvector, `POST /search`, ingestion pipeline, `slot_extractor`, `tag_cafe` in `app/ingestion/tagger.py`, and populated `cafes` rows from Google Places API (New).

**Architecture (Week 2):**

- **Reviews reality check:** Google Places `places/{id}` returns at most **5 reviews** in the field mask response. There is **no** supported way to fetch 50 reviews per place from the official API without scraping (out of scope). The v2 tagger must treat **≤5 review texts + `editorialSummary` (when present)** as the full evidence bundle for extraction and for faithfulness-style eval.
- **Code split:** Implement `review_tagger_v2` as a dedicated module; **do not** change `slot_extractor` in Week 2.
- **Eval contract:** Golden file `backend/app/eval/golden_set.json` (30 items). Baseline artifact `docs/eval-results/YYYY-MM-DD-v1.json` with at least `context_precision`, `faithfulness`, `answer_relevancy` (definitions align with design spec §6 “Week 2”).

**Tech Stack (additions):** Keep Week 1 stack. Add eval dependencies (see Task 0): typically `ragas`, `datasets`, and compatible OpenAI / LangChain pieces per the version pins you choose—**pin versions in `pyproject.toml`** after the first successful `uv lock`.

**Prerequisite checklist (verify before Task 0):**

- [ ] Week 1 **complete**: `cafes` has real rows (IDs stable); ingestion and `/search` work locally.
- [ ] Docker Desktop + `infra/docker-compose.yml` Postgres running; `DATABASE_URL` in `backend/.env` matches.
- [ ] `OPENAI_API_KEY` and `GOOGLE_PLACES_API_KEY` set; raw place JSON cache under `backend/data/places_raw/` exists **if** you plan to rebuild inputs without re-calling Details (recommended for reproducibility).

## Task 6: Eval Harness — Retriever + Three Metrics

**Files:**

- Create: `backend/app/eval/ragas_baseline.py` (or `backend/scripts/run_ragas_baseline.py`)
- Create: `backend/app/eval/metrics.py` — thin wrappers if you implement spec metrics manually vs library metrics

**Per spec “Eval methodology”:**

1. For each golden query, run your **Week 1 retriever** to get **top 5** cafe IDs + their rows.
2. **`context_precision`:** fraction of returned cafes whose `id` appears in `expected_cafe_ids`.
3. **`answer_relevancy`:** semantic similarity between each returned cafe’s **`ambience_text`** (or concatenated) and the query—use embedding cosine **or** RAGAS `AnswerRelevancy` with your adapter.
4. **`faithfulness`:** degree to which `ambience_text` is grounded in the **stored review texts** (and editorial summary) for that cafe—a small LLM judge or RAGAS `Faithfulness` with `contexts` = list of review strings.

**Notes:**

- If the stock RAGAS dataset schema fights your stack, it is acceptable to **compute numerically equivalent metrics** and still label the JSON keys `context_precision`, `faithfulness`, `answer_relevancy`—document the formula in the JSON `meta` block.
- Keep runs **deterministic** where possible (`temperature=0` for judges).

- [ ] **Step 1: Implement `run_baseline() -> dict`** returning aggregate means + per-query breakdown.

- [ ] **Step 2: Log prompt versions used** (slot_extractor hash/version if available, review_tagger v2 version from DB).

## Appendix B: Risk Register

| Risk | Mitigation |
|------|------------|
| RAGAS version churn / LangChain pins | Pin in `uv.lock`; record versions in eval JSON `meta`. |
| Eval cost (many LLM calls) | Cache judge outputs per `(cafe_id, query)` during dev; reduce golden set temporarily only for debugging, not for committed baseline. |
| `expected_cafe_ids` stale after re-ingest | Re-label golden set when `cafes` are wiped; store `golden_set.version`. |
| Faithfulness noisy with 5 short reviews | Prompt judge to abstain (“insufficient evidence”) and score partial credit. |
